# Governance — rustmanifest

## Maintainers

The maintainer set is listed in `.github/CODEOWNERS`. The current sole maintainer is **@RAprogramm**. Additional maintainers are added by an explicit PR signed by an existing maintainer; the PR must update `CODEOWNERS`, this document, and `docs/THREAT_MODEL.md` (adversary list).

## Versioning

The workspace contains multiple crates with independent SemVer:

| Crate | Public surface | Notes |
|-------|----------------|-------|
| `rustmanifest-schema` | JSON Schemas, Rust types | Breaking schema change → major bump |
| `rustmanifest-rules-core` | Rule definitions, IDs, severities | Adding a rule → minor; tightening severity → major; removing a rule → major after deprecation cycle |
| `rustmanifest-engine` | Public traits and analyzer entry points | Breaking trait change → major |
| `rustmanifest-config` | `rustmanifest.toml` shape | Breaking shape → major after deprecation cycle |
| `rustmanifest-report` | Output formats (JSON, SARIF, TTY) | Adding fields → minor; removing fields → major |
| `rustmanifest-mcp` | MCP tool surface | Tool surface follows MCP protocol revisions |
| `rustmanifest-lsp` | LSP server | Follows LSP spec version |
| `rustmanifest-cli` | Command-line interface | Breaking flag changes → major after deprecation cycle |

The `rustmanifest-cli` binary is the primary user-facing release artifact and follows its own SemVer track.

## RFC process

Significant changes require an RFC merged before implementation:

- New rule tiers.
- New MCP transports or auth flows.
- Breaking changes to any public API or rule severity.
- Changes to the rules-pack format or schema.

Procedure:

1. Copy `docs/RFCS/0000-template.md` to `docs/RFCS/NNNN-short-slug.md` where `NNNN` is the next free number.
2. Open a PR with the RFC. The title is `rfc NNNN <short slug>`.
3. The RFC stays open for at least **10 days** of public review before merge.
4. The maintainer set decides; disagreement is recorded in the RFC's `Drawbacks` section.
5. Merged RFCs are tracked in `docs/RFCS/INDEX.md` (auto-generated by Phase 5 tooling).

RFCs may be withdrawn by their author or rejected by maintainers; both outcomes are recorded in the RFC file with a status header.

## Deprecation policy

- Rules and public API items marked `#[deprecated]` (or with a deprecation note for non-Rust artifacts) remain functional for **one minor cycle** of their owning crate.
- They are removed in the next major release after the minor that marked them.
- CI gates breaking changes via `release-plz`'s `semver_check`.

## Severity governance

Increasing a rule's default severity is a **major** version bump of `rustmanifest-rules-core`. Decreasing severity is a **minor** bump. Adding a brand-new rule at any non-`error` default severity is a **minor** bump; new rules defaulting to `error` require an RFC.

## Release cadence

- Patch releases: as needed for bug fixes and security advisories.
- Minor releases: every 4–6 weeks, batched.
- Major releases: at most twice per year per crate, batched.

`release-plz` automates the release PR; merging it triggers crates.io publication and the binary release pipeline.

## Funding and conflicts

Funding sources are listed in `.github/FUNDING.yml`. Contributors disclose conflicts of interest in their PR description when relevant. Maintainers recuse themselves from reviews where a conflict applies.
